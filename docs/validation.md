# Bench validation

## Status

The base and optimized headless CUDA images built, flashed to the JAJ NVMe,
and passed authenticated SSH, native boot verification, filesystem growth and
CUDA correctness checks. Each completed three qualified cold boots. The
optimized image also passed native Bonsai inference and all seven HTTP/text/vision
checks. [Build validation](build-validation.md) records
the configurations, artifact hashes and completed build checks.

The external-only flash retained the bench's existing custom minimal R39.2.1
UEFI/QSPI from PR 109. These measurements do not qualify the full UEFI firmware
generated by this repository. No camera or PCIe FFC endpoint is connected.

## Physical Ethernet link — separate readiness criterion

The clarified target is under six seconds from power applied, including POR,
to physical Ethernet link, which must then remain uninterrupted. **The current
profile fails this requirement.** Three additional cold boots with a direct AX88179B
PC adapter observed first carrier at **5.587 s median (5.403–5.712 s)** from
the supply command. Each then showed one sampled drop and recovery: last-up
was **16.678 s median (16.345–16.719 s)**, with link still up at the end of the
40-second capture. All boots also passed native boot verification and CUDA.

[The link investigation](early-ethernet.md) and
[sanitized measurements](results/yocto-r39-ethernet-boot.json) preserve each
transition and actual polling gaps. These are peer-reported carrier timestamps,
not electrical input/link edges; nominal polling is 20 ms and USB/driver latency
also applies. Initial carrier within six seconds was observed on all three
boots, but continuous link from that point was not achieved. The required POST
checks remain undefined.
The retained firmware and OS were unchanged for this measurement.

## Optimized Yocto image — 2026-09-21

The measured configuration combines `kas/jaj.yml`, `kas/bonsai.yml`,
`kas/fastboot.yml` and `kas/no-camera.yml`. It uses MAXN_SUPER mode 0 with
normal dynamic clocks, quiet console output, asynchronous BPMP debugfs with
`delay_ms=0`, and the optional camera-mux overlay. The first provisioning boot
is excluded. All three subsequent cold boots passed native boot verification,
authenticated SSH and full verification of the CUDA smoke result.

| Cold-boot milestone | Median | Observed range (3 boots) |
|---|---:|---:|
| Linux multi-user target marker | 13.363 s | 13.353–13.574 s |
| First observed verified CUDA probe | 13.539 s | 13.535–13.756 s |
| UART username prompt displayed | 15.587 s | 15.568–15.783 s |
| USB-network SSH identification banner | 15.918 s | 15.904–15.942 s |

[Sanitized boot samples](results/yocto-r39-fast-boot.json) include the same
roughly two-second board POR delay and SCPI command-send reference as the base
measurements. Median CUDA readiness improved by **6.396 s (32.1%)** from the
base Yocto image, and was 0.308 s earlier than the recorded Ubuntu median.
These short runs do not establish a general OS performance advantage. None
of these power-on readiness milestones is under ten seconds, and CUDA
readiness does not include loading a model or starting ARK-OS.

The timing change measures the combined configuration, not isolated savings
from each option. The diagnostic provisioning trace confirms BPMP debugfs
completed asynchronously, the camera mux was disabled and absent IMX219
probes disappeared. Quiet logging also reduces early kernel time. The empty
FFC controller remains enabled at Gen2 and its probe still occupies about
2.1 seconds before root mounting in that trace. No attached FFC endpoint was
available for functional testing; this profile retains its Linux driver and
device-tree configuration.

The optimized CPU/CUDA tests passed with `jetson_clocks`: SHA-256
1,205.10–1,205.29 MiB/s and vector-add 93.380–93.386 GB/s. Normal dynamic
clocks and native fan control were restored afterward.
[Sanitized performance samples](results/yocto-r39-fast-performance.json)
record the settings and measurement limits. One-second telemetry sampling
missed the short GPU workload, so it cannot establish its peak utilization,
power or absence of throttling.

## Yocto base image — 2026-09-21

This is the unmodified pinned kernel and OE4T initramfs, before selecting
`kas/fastboot.yml` or `kas/no-camera.yml`. MAXN_SUPER mode 0 was selected in the
private build configuration. Normal dynamic clocks were used for cold boots.

| Cold-boot milestone | Median | Observed range (3 boots) |
|---|---:|---:|
| Linux multi-user target marker | 19.759 s | 19.348–20.342 s |
| First observed verified CUDA probe | 19.935 s | 19.533–20.523 s |
| UART login prompt displayed | 21.988 s | 21.585–22.572 s |
| USB-network SSH identification banner | 22.586 s | 22.225–22.928 s |

[Sanitized boot samples](results/yocto-r39-base-boot.json) use the same SCPI
command-send reference as the Ubuntu comparison below. All accepted Ubuntu
captures showed an automatic-login announcement followed by a shell prompt;
Yocto showed a normal username prompt. The UART timestamps record these different
prompt events and do not establish equivalent authenticated-console readiness.

The provisioning boot, including first-boot root filesystem growth, is excluded.
The initial USB diagnostic run is separate: CUDA completed in 21.693 s but SSH
had no route within 40 s. Upstream random gadget MACs and a one-address DHCP pool
for two USB interfaces caused that access failure. The repository now derives
stable per-module MACs and provides two leases; both identities remained stable
through all three accepted cold boots.

The flashed base archive SHA-256 is
`1e9fda6284781f82f732044e5cf9b041bb18052c90538cf338528537d7988abf`.
The three source-matched USB configuration files were applied before the accepted
cold boots. The retained firmware also reapplies its old dual-IMX219 overlay,
causing absent-camera probes; the separate no-camera variant addresses this
without suppressing required firmware overlays.

The base CPU/CUDA tests passed under MAXN_SUPER with `jetson_clocks`: SHA-256
1,205.4–1,205.5 MiB/s and vector-add 95.27–95.30 GB/s. These are comparisons of
complete image stacks: Yocto uses GCC 15.3.0, `-O2` with hardening and OpenSSL
3.5.8; Ubuntu uses GCC 13.3.0, Release `-O3` and OpenSSL 3.0.13. Both use nvcc
13.2.86 and SM87. [Sanitized performance samples](results/yocto-r39-base-performance.json)
include clock, temperature and fan evidence. The same-source workloads and their
limits are described below.

## Ubuntu baseline — 2026-09-21

ARK Just a Jetson with Orin NX 16GB, Ubuntu 24.04, L4T R39.2.1,
Linux 6.8.12-1021-tegra, and the existing fast-boot firmware/rootfs from
[ark_jetson_kernel PR 109](https://github.com/ARK-Electronics/ark_jetson_kernel/pull/109).
The ARK-OS stack remains installed. Only the boot-measurement marker services
were added temporarily; they were removed after measurement.

| Cold-boot milestone | Median | Observed range (3 boots) |
|---|---:|---:|
| Linux multi-user target marker | 13.597 s | 13.363–13.676 s |
| First verified CUDA integer computation | 13.847 s | 13.618–13.932 s |
| UART login prompt displayed | 13.927 s | 13.674–14.001 s |
| USB-network SSH identification banner | 11.982 s | 11.634–14.783 s |

These are host monotonic times from sending the supply's output-on command.
They include the board's roughly two-second POR circuit delay. The electrical
power edge was not measured. UART times include serial transmission/host read
latency; Linux uptime values are retained separately in the JSON.

A login prompt does not measure successful authentication. An SSH banner does
not establish that an application is ready. The CUDA milestone requires an
actual GPU kernel plus full output verification; it is independent of ARK-OS
API readiness and is not a model-loading or inference benchmark.

The first instrument trial routed markers to the display console and is not
included. Another trial lost the supply's USB connection before power-on and
is also excluded. The third accepted sample powered on after that connection
was re-established, so its power-off interval was longer than the first two
(minimum eight seconds). All accepted runs include a complete power removal
and a successful CUDA result. No camera is connected.

[Sanitized boot samples](results/ubuntu-r39-baseline-boot.json) preserve each
accepted observation and aggregation rules. Device identities and raw UART
logs are excluded.

## Ubuntu performance baseline

Both tests used native MAXN_SUPER mode 0 with `jetson_clocks`. The same C++/CUDA
sources are packaged by the Yocto `ark-bench` recipe. Ubuntu compilation used
GCC 13.3.0, nvcc 13.2.86, Release optimization and SM87.

| Test | Result | Scope |
|---|---:|---|
| SHA-256 | 1,204.6–1,205.0 MiB/s | One CPU thread; 256 MiB per timed sample; OpenSSL 3.0.13 |
| CUDA vector add | 95.61–95.65 GB/s | Logical effective bandwidth; 4,194,304 uint32 elements; 200 launches/sample |
| CUDA smoke | Pass | All 65,536 output elements verified |

Each throughput test records three timing samples in one process after warmup.
Vector-add bandwidth counts two reads and one write; it is neither inference
throughput nor a measurement of physical DRAM bus traffic. Initialization,
allocation, copies and first-kernel timing are reported separately.

[Numeric performance samples](results/ubuntu-r39-baseline-performance.json)
include CUDA/runtime versions and correctness checks. The Yocto compiler and
OpenSSL version differ, so comparisons will identify those differences rather
than attribute every change solely to the operating system.

Measured Ubuntu/Yocto Bonsai comparisons and exact matching commands are in
[bonsai.md](bonsai.md). The [early Ethernet investigation](early-ethernet.md)
tracks the separate sub-six-second physical-link requirement; CUDA and SSH
readiness do not establish that result or completion of unspecified POST checks.

## Repeating the measurements

Use `scripts/measure-boot.py --help` for explicit UART and power-supply selection.
Halt/shut down the target cleanly before cutting power, and verify storage is
read-only. The tool preserves supply voltage/current/protection settings and
checks the selected instrument's identity. Its raw output must remain private.

Aggregate three new run directories with:

```sh
python3 scripts/summarize-boot.py run-1 run-2 run-3 \
  --terminal-kind login --output boot-summary.json
```

The summarizer excludes instrument failures, distinguishes host and target
clocks, and leaves missing milestones empty. Use `scripts/bench-target.py`
with an explicitly trusted SSH host key to collect CPU/CUDA results from a
running image. See the [benchmark package](../meta-ark/recipes-support/ark-bench/README.md)
for exact workload definitions.
